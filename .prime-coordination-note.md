# Koordinace po sloučení TUI do main

Zapsáno 2026-10-11. Cílem je, aby nikdo nepřišel o práci při sloučení.

## Co se stalo

Větev `tui/upgrade-omp-parity` byla sloučena do `origin/main` jako `31cd771`.
Owner to výslovně schválil (možnost B, celá větev).

Před sloučením jsem zjistil, že větev nenese jen TUI práci. Nese na sobě
**20 commitů cizí práce**, které přišly s větví při jejím založení, včetně
`refactor: rename Void to Nomo across the product surface`. To by do main
vtáhlo přejmenování celého produktu.

## Jak se konflikty řešily

Rozhodující bylo zjištění, že moje vlastní práce je **21 souborů výhradně
v `packages/cli/src/tui/`**, importuje relativními cestami a **nulu reference
na `@void/*`, `@nomo/*` ani `void_` / `nomo_`**. Podle toho:

| Oblast                             | Rozhodnutí | Proč                                                      |
| ---------------------------------- | ---------- | --------------------------------------------------------- |
| `packages/cli/src/tui/**`          | větev      | skutečná práce                                            |
| `docs/`, `.opencode/`, `README.md` | main       | dokumenty jsem nezměnil, konflikty jsou cizí přejmenování |
| `package.json`, `pnpm-lock.yaml`   | main       | `@void/*` je záměrná volba mainu                          |
| 33 souborů s `@nomo/*`             | main       | sjednoceno zpět na `@void/*`                              |
| 38 souborů s `nomo_workspace_*`    | main       | main má `void_workspace_*`                                |
| `server.ts`, `workbench/index.ts`  | obě strany | obě měly různé platné změny                               |

## Past, na kterou narazil každý, kdo merge udělá znovu

Auto-merge nechal v `apps/control-plane/api/server.ts` směs: kód čte
`env.VOID_PERMISSION_MODE`, ale allowlist deklaroval `NOMO_PERMISSION_MODE`.
To se projevilo jako **7 selhávajících control-plane testů** a jako chyba
buildu (`Cannot find module '@void/proxy'`). Po `pnpm install` a sjednocení
názvů prochází 21/21.

Pokud váš merge přinese podobné selhání, hledejte smíšené názvy, ne logiku.

## Co je potřeba udělat v `.worktrees/nomo-agent-identity-fleet`

Větev `docs/nomo-agent-identity-fleet-2026-10-08` má 3 commity nad novým
`main`. Před sloučením do main ji prosím zrebasejte:

```
git rebase origin/main
```

Co se při tom může potkat:

1. **Dokumenty.** Sloučení respektovalo smazání dokumentů, které `main`
   měl smazané. Pokud vaše větev staví na soubor, který `main` smazal,
   rebase to označí jako konflikt add/add nebo modify/delete.
2. **`void_` vs `nomo_`.** Nástroje jsou `void_workspace_list`,
   `void_workspace_read`, `void_workspace_write`, `void_workspace_delete`.
   Pokud máte ve fixturech nebo testech `nomo_workspace_*`, je to po
   sloučení neexistující nástroj.
3. **`@void/*` balíčky.** Ne `@nomo/*`.
4. **Env proměnné** jsou `VOID_*`, ne `NOMO_*`.

## Kdo s čím nesmí kolidovat

- **TUI práce:** pouze `packages/cli/src/tui/`. Owner schválila, že tohle je
  moje území a ostatní do něj nesahají.
- **Identity fleet:** `.worktrees/nomo-agent-identity-fleet`, větev
  `docs/nomo-agent-identity-fleet-2026-10-08`. Do main po rebase, prosím
  žádným způsobem nechte `main` sloučit bez rebase, jinak se znovu objeví
  stejná směs `@void` a `@nomo`.
