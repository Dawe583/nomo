1. Executive summary

Agents that use MCP tools can write to databases, repositories, cloud services and third-party APIs. After an incident, an operator needs to answer five questions: which registered agent and run made the call, what scope and policy applied, who approved a held write, whether the target received it, and whether a revoke prevented the next call.

NOMO is an Agent Identity and Fleet Control Plane for MCP-capable agents. It places a trusted proxy in the agent's tool path. The proxy binds each call to a principal, workspace, agent and run; checks scope; classifies the call; evaluates an ordered policy; writes decision evidence before forwarding a high-risk write; and records the result or an explicit unknown outcome after the upstream responds.

The design is deliberately fail-closed. Unknown tool, unclassified call, invalid policy, ledger append failure, invalid facts or internal proxy error all deny. An observe-only mode exists but must be selected explicitly.

Three things the paper is careful about:

  1. The ledger signature proves that bytes came from a process holding a key. Under the current local deployment, the recorder, signer and verifier share one operating-system user, and the verification key default lives beside the signing key. A plain local signature therefore does not protect against the agent itself. Pinning a verification key out of band is the defense, and it is not the default.
  2. Recovery and undo are real technical capabilities for specific connectors and effect classes. They are not the primary product direction. The context pack states that recovery is not the current primary wedge.
  3. The market for identity, credential brokerage, MCP gateways and runtime control is active. NOMO does not claim an empty market or a first position. Current products named in the MVP spec include Microsoft Entra Agent ID, AWS Bedrock AgentCore Identity and Cloudflare MCP server portals.

Current status, by tag:

  • Implemented: a STDIO proxy with policy, hash-chained signed JSONL ledger, operation journal, recovery adapter contract, CLI, control-plane API surface and a desktop shell.
  • Planned for the 2026-10-11 demo: an inbound loopback Streamable HTTP MCP endpoint, a local test issuer, a 60-second opaque run token, one disposable target and one constrained Harness run.
  • Planned for product v1: MCP HTTP authorization conformance, principal registry, revocation with acknowledgement, the Harness on the same path, and an independent evidence verification path.

2. Problem statement

2.1 The operator's questions

The MVP spec defines the primary operator as a team owner responsible for coding or workflow agents that can write to databases, repositories, cloud services or other MCP tools. The operator needs to answer:

  • Which registered agent and run made this call?
  • What scope and policy applied?
  • Who approved it, if it was held?
  • Did the target receive it?
  • Does a revoke prevent the next call?

2.2 Why existing answers are partial

Identity providers can issue credentials to an agent. Credential brokers can scope a token to a resource. MCP gateways can route and log tool calls. Audit logs can record what a service says happened. Each addresses part of the problem. The gap NOMO targets is narrower: a single enforcement path in which every tool call through the proxy has a decision record before dispatch, a bounded fast path for reads and low-risk calls, a full policy and evidence path for high-risk writes, and an operator view of dispatched work whose outcome is still unknown.

NOMO does not claim this gap is unoccupied. The MVP spec names its wedge as a hypothesis: one governed write with four named owners (agent principal, scope and policy, control approval, incident response).

2.3 What NOMO is not

  • It is not an identity provider and does not replace one.
  • It is not a backup product. Recovery is a technical capability, not a backup.
  • It is not a production key management service.
  • It is not a proof that declared facts are true, that a human approval was authenticated, or that the target system is healthy (see section 10.4).

3. Product direction and scope

3.1 Direction

The context pack (docs/CONTEXT.md) defines the product as an Agent Identity and Fleet Control Plane. Its key properties:

  • The runtime binds each tool call to a trusted principal, workspace, registered agent and run.
  • All calls receive identity and scope checks and emit a minimal metadata event.
  • Reads and low-risk calls use a bounded fast path. The fast path still passes through the trusted proxy and does not bypass identity checks.
  • High-risk writes receive the complete policy and durable-evidence path.
  • Operators can inspect decisions, approve or deny a held operation, revoke a run or agent, and see unresolved dispatched work.

The coding-agent Harness is a required host integration and a product-v1 release gate. It is not a separate product. Its runs use the same identity, token, proxy, policy and ledger path as other managed agents.

The context pack supersedes recovery-first positioning in earlier strategy documents. Existing recovery, connector, policy, ledger, verification, privacy and operational contracts remain technical capabilities unless a dated decision changes them.

3.2 Scope tiers

Source: MVP spec, Scope section.

Sunday demo (target 2026-10-11): one trusted Workbench run mapped to one registered principal, agent and workspace; one local test issuer; one workspace; one loopback inbound Streamable HTTP MCP endpoint; one disposable MCP target (candidate: fixtures/e2e-server.mjs with fixtures/e2e-policy.yaml, to be confirmed by a smoke test). Proves a read on the fast path, and high-risk Allow, Deny and Hold, with Hold bound to the exact canonical operation digest and a verified local operator. Includes a local kill switch that stops the next call after acknowledgement. Learning is disabled.

Product v1: principal registry; standard MCP HTTP authorization; run grants that are short-lived, scoped and revocable; durable pre-dispatch decision record with a linked result or unknown outcome; standalone ledger verification; separate run stop, agent revoke and fleet revoke, where fleet success is returned only after enforcement nodes acknowledge; Harness on the same path with approved-proposal activation; control-plane views of inventory, events, approvals, acknowledgements and unresolved outcomes.

Full product: multi-tenant isolation, role-based access, SSO, hosted key management, audited integrations, broad host and connector support, resilient fleet revocation, operational support, independent evidence export, enterprise availability. Each host must declare which authentication, policy, ledger and kill-switch guarantees it supports.

3.3 Non-goals

From the MVP spec. No production deployment or broad market claim by 2026-10-11. No full MCP OAuth, third-party HTTP login, SSO or tenant billing in the demo. No OAuth identity over STDIO in the demo. No distributed fleet acknowledgement or kill SLA in the demo. No claim that a kill cancels an in-flight call or reverses its effect. No automatic policy learning, autonomous approval or cross-workspace retrieval. No Git history rewrite, no push to main, no PR and no GitHub Actions trigger in this work stream.

4.2 Request path

The sequence below is the design in the context pack and the MVP spec. The STDIO implementation covers steps 1 to 6 today. Inbound HTTP (step 1 for HTTP) is planned.

  1. The agent sends an MCP request to the proxy. Over STDIO today; over loopback Streamable HTTP for the demo.
  2. The proxy validates the caller's run grant (planned for HTTP; the STDIO path is governed by process trust, see 7.4).
  3. The proxy resolves the tool to a registry entry. An unknown tool or unclassified call is denied.
  4. The proxy canonicalizes arguments and computes an argument digest. Payloads are not stored; digests are (OPERATIONS.md, Ledger directory layout).
  5. Policy is evaluated. Rules are ordered; first match wins. A missing or invalid policy is a startup failure in fail-closed posture.
  6. The outcome is applied:
  • Allow: decision evidence is appended, then the call is forwarded.
  • Deny: decision evidence is appended, the call is not forwarded, and an MCP error with the rationale is returned.
  • Hold: decision evidence is appended, the proxy waits for an operator decision bound to the exact digest, grant state is rechecked, and only then is the call forwarded.
  • Observe-only: recorded and forwarded without enforcing deny or hold. Only when selected explicitly.
  1. After the upstream response, the result or an explicit unknown outcome is appended.

If the ledger append of decision evidence fails before dispatch, the call is denied (MVP spec, Security requirement 5).

4.3 Read path and fast path

Every call receives identity and scope checks and a metadata event. Reads and low-risk calls skip the durable policy and operator path and go to the bounded fast path. The fast path is not a bypass: it still traverses the proxy. The MVP spec makes no latency claim. p50 and p95 for the fast path and high-risk path are to be measured separately before any product target is set.

4.4 Transports

STDIO (implemented). The proxy spawns the upstream as a child process. The proxy removes its own signing key variable from the child environment (packages/proxy/src/transport/stdio.ts:113, per THREAT-MODEL.md). The child still runs as the same operating-system user and can read the signing key file (section 6.4).

Streamable HTTP inbound (planned). Loopback only for the demo. Must implement the MCP SDK's server API. The existing HTTP code in the proxy is an upstream client, not an inbound server (MVP spec, Scope). Open question 1 in section 13 covers whether the pinned SDK can share the interception pipeline.

Upstream HTTP (implemented). The proxy calls an upstream MCP server over HTTP as a client. The upstream receives its own least-privilege credential, never the proxy token (context pack, Trust and enforcement model).

5. Trust and enforcement model

5.1 Identities

Three identities are distinct (context pack):

  • Operator account: a human administrator, authenticated in the browser session.
  • Registered agent principal: the identity an agent acts as.
  • Run: one execution of an agent.

A web session never substitutes for an agent grant. Caller-supplied agentId and runId are metadata, not authority. The trusted Workbench or broker binds principal, workspace, agent and run.

5.2 Outcomes

Allow, Deny, Hold and observe-only are explicit outcomes. Unknown identity, scope, policy, broker, revocation or ledger state fails closed. Observe-only is opt-in, visible and never an error fallback (context pack; MVP spec, Security requirement 6).

5.3 Hold semantics

A held operation is approved against the exact canonical operation digest, the policy version and a verified operator. Scope, expiry and revocation are checked again before dispatch (context pack). The MVP spec adds: if the grant expired after approval, issue a new scoped grant or reject the operation (Security requirement 4).

Per-hold nonce. Every hold carries a nonce, so a stale decision file cannot replay onto a later hold after a restart (OPERATIONS.md, Approvals). The approval surface is a development surface and is not authenticated (OPERATIONS.md, Approvals). Human identity behind an approval is therefore unproven in the current repository.

5.4 Dispatch and stop

Evidence before dispatch: decision evidence is appended before any high-risk write is forwarded. If the append fails, the write is not dispatched (context pack, Trust and enforcement model).

Stop: a stop blocks later calls after acknowledgement. It does not cancel a call already dispatched and does not reverse side effects. A timeout is an unresolved outcome until reconciled against the target. It is never reported as cancelled or reverted (context pack; MVP spec, Security requirement 7).

5.5 Secret handling

Token, prompt and secret values never enter logs, events, ledger payloads, screenshots or durable workspace state (context pack). Tokens appear only in the HTTP Authorization header, never in URL query strings, prompts, logs, events, ledger payloads, screenshots, browser storage or upstream MCP calls (MVP spec, Security requirement 2).

Browser separation. The browser operator session and agent credentials are separate. Agent tokens must not be stored in browser storage or durable user settings (context pack).

6. Ledger

6.1 Properties

The ledger is append-only, hash-chained and signed per entry. Each stored entry is one JSON line containing: workspace, sequence number, body (time, tool, class, decision, argument digest, and attribution where present), previous hash, entry hash, key id, algorithm and signature (OPERATIONS.md, Ledger directory layout). Ledger stores digests, not payloads.

Entry hash: sha256 over the domain label "void.ledger.entry.v1|", the previous hash, "|", and the canonical JSON of the body (packages/ledger/src/canonical.ts:94-105, per THREAT-MODEL.md section 3).

Signature pre-image: "void.ledger.<version>|" + algorithm + "|" + key id + "|" + entry hash (packages/ledger/src/index.ts:69-77, per THREAT-MODEL.md section 3).

Canonicalization is recursive, so nested arguments are covered by the signature (THREAT-MODEL.md section 3).

The domain labels (void.ledger.*) are kept for compatibility with signed existing ledgers. The context pack says persisted identifiers are not silently renamed.

6.2 Storage: the two documented stores

The context pack and DECISIONS.md section 2, as quoted in THREAT-MODEL.md and OPERATIONS.md, describe two stores behind one interface. This paper does not describe more.

Resolution order when no DATABASE_URL is set: NOMO_LEDGER_URL, then DATABASE_URL, then the local JSONL store if its directory is writable (THREAT-MODEL.md section 2). Multiple proxies on one JSONL file are unsafe (OPERATIONS.md, Fail-closed section).

Verified (documented-verified, per DECISIONS.md section 2 as quoted in THREAT-MODEL.md section 2.3): in public schema, a repository migration command dropped a populated ledger table and its triggers with a success message. In a dedicated schema the same test left everything intact. As the application role, UPDATE, DELETE, DROP TRIGGER and DISABLE TRIGGER ALL were refused.

Limit: a database superuser bypasses grants and triggers. The chain and signature are what hold against that actor, and only if the verification key is outside the actor's reach (section 6.4).

6.3 Tiers

The repository does not describe a four-tier ledger. The paper refers to the two stores in 6.2 and the verification sources in 6.4 as the only documented distinctions.

6.4 Signature scheme

Algorithm. ed25519, via node:crypto. No extra dependency for the signature itself (DECISIONS.md, quoted in THREAT-MODEL.md). Every entry is signed, not only a head. A periodic signed checkpoint over the head supports attestation (OPERATIONS.md, Attestation flow).

Interface. KeyProvider exposes currentKeyId, sign(input, keyId?) and publicKey(keyId) returning SPKI DER. It is asynchronous and never returns private key material (THREAT-MODEL.md, Key custody; DECISIONS.md section 3 as quoted).

Key id. Derived from the public key: "ed25519:" followed by the first 16 hex characters of the SHA-256 of the SPKI (THREAT-MODEL.md section 3, as quoted).

Algorithm agility. The verifier rejects any algorithm other than ed25519 (packages/ledger/src/verify.ts:123). Post-quantum (ML-DSA-65) and ECDSA P-256 are not implemented.

Key generation and file custody. Keys are generated with generateKeyPairSync("ed25519") and written with O_CREAT | O_EXCL at mode 0600 (packages/ledger/src/sign.ts:147-151). readExistingKey rejects symlinks, non-regular files and wrong modes (sign.ts:135-138; hardening.ts:75-96). A Windows ACL check permits only the current SID, SYSTEM and Administrators (hardening.ts:8-64, :30).

Locations (THREAT-MODEL.md section 2.1):

Keychain. The desktop keychain holds the workspace encryption key, not the ledger signing key (THREAT-MODEL.md section 2.2, citing apps/desktop/src-tauri/src/keychain.rs). Moving the signing key into a keychain would not, by itself, separate it from the agent running in the same process.

Documented-verified attack (OPERATIONS.md, referring to docs/EVIDENCE-FIXES-VERIFICATION.md F1). After unlink and recreate of the 0400 trust file alongside a replaced key file, the resolved key reported source trust-file, operatorSupplied false, degraded false, and the forged chain verified ok=true. The paper's earlier drafts cited this drill to OPERATIONS.md; the record is in EVIDENCE-FIXES-VERIFICATION.md.

The trust file stays at its default path. OPERATIONS.md argues that no location on a single-user host is out of reach of a same-uid attacker, and that moving it would strand keys already provisioned.

Provisioning. nomo init --pin-verify-key anchors the key at ~/.nomo/keys/dev-ed25519.pkcs8 at the moment it runs. It detects only a later change. nomo init --from-spki <base64> anchors a key the operator holds elsewhere (OPERATIONS.md).

Two key files exist under ~/.nomo, and only one is the anchor. ~/.nomo/keys/dev-ed25519.pkcs8 signs the ledgers in ~/.nomo/ledger and is the trust anchor. <data dir>/keys/dev-ed25519.pkcs8 signs the workbench document ledger and is a second recorder identity, not a second location for the first. Earlier behavior anchored the wrong key on the default path. The command now prints both key ids and names the one anchored (OPERATIONS.md).

6.5 Verification

nomo verify --ledger <dir-or-file> checks sequence order, previous-hash links, body hashes and signatures when a key is available. A failure exits non-zero and names the first bad entry. With no key, the output reports "verification key: none, signature NOT VERIFIED" and checks hash links only (OPERATIONS.md, What every surface reports).

Verification against an attestation or a published anchor file is available through verify --attestation and verify --anchors. An anchor is checked only when a verification key is available; without one, the command refuses (OPERATIONS.md, Verify a ledger or export).

Truncation. A valid prefix verifies. Truncation is not detectable from the local chain alone (OPERATIONS.md, The anchor is what makes truncation detectable).

Anchors. nomo attest --ledger <file> --anchor <anchors.jsonl> verifies the chain, signs the head, writes a retained copy under <ledger dir>/attestations/<head-seq>.json and appends the signed head to the named anchor file. The anchor file is appended to, never rewritten, and a head that goes backwards or conflicts is refused (OPERATIONS.md, Attestation flow).

An anchor detects tampering by a third party, not by the agent itself. It is only as strong as the location of the anchor file: a path the agent process cannot write, a read-only mount, a copy held by a third party, or a file forwarded out of band. The command warns on every write when the anchor sits inside the directory the agent writes (OPERATIONS.md). The anchor is not non-repudiation and is not a claim of trust level L2 (OPERATIONS.md).

6.6 Export bundles

nomo export --ledger <file> --state <state-dir> --bundle <bundle-dir> writes a bundle of four sections and a manifest. The manifest is written last. Sections:

  • ledger.jsonl: the verified workspace ledger.
  • journal.jsonl: the operation journal, replayed through the transition tables on export and load.
  • vault-manifest.json: the vault inventory by digest and byte length. Artifact bytes stay encrypted at rest and are not copied.
  • capability.json: what this build can export, the ledger read limits, and the operation and recovery-job stage universe from the journal transition tables.

Each section carries a record count, byte length and SHA-256, and each signed section carries the sequence range it claims. The printed manifest SHA-256 must be recorded out of band. That is the completeness proof: a history whose tail was cut is still internally consistent, so a reviewer without an anchor cannot distinguish an honest bundle from a rewritten one (OPERATIONS.md, Export bundles).

Verification is fail-closed. Export verify with --anchor and --state checks digests, counts, ranges, chains and transitions, and checks journal signatures only when --state supplies the retained key. Without --state it reports "journal signatures not checked" (OPERATIONS.md).

This proves what the bundle contains. It does not prove the vault bytes are recoverable and is not an operational certification (OPERATIONS.md).

6.7 Metrics

nomo metrics recomputes counters from existing ledger, journal and vault data. Nothing new is persisted. Label sets are closed; no PII, secrets or workspace labels appear in sample names. A named ledger must verify before it is counted. Stages that never happened report zero, so failed, unknown and conflict work is not hidden by omission (OPERATIONS.md, Metrics).

Not covered: capture latency, reconciliation time, recovery success rate and connector coverage, because the surface does not read the required timestamps and receipts.

6.8 Key rotation

Rotation is not supported as a user flow (OPERATIONS.md, Key rotation).

What happens: entries signed by a retired key carry its key id. With only the new verification key, the chain is refused with "entry 1 has no public key for dev-ed25519:<old id>". nomo attest exits 1 with that error. nomo export --ledger does not verify, so it can still succeed, and a workflow that exports after a rotation and then attests discovers the problem at the second step.

A drill on 2026-10-03 added devKeyRing(dir), a KeyProvider that answers publicKey(id) for the current key and for each retired public key under <dir>/retired/<keyId>.spki, and rotateDevKey(dir), which retires the outgoing public SPKI and installs a new private key through the same O_EXCL 0600 path. sign(input, keyId) honours the key id it declares and throws a named error otherwise. The test in packages/ledger/src/rotation-drill.test.ts verifies a two-key chain (checked === 4, key ids [A, A, B, B]) through the ring and through jsonlStore.verify. The shipped single-key trust decision still refuses the same chain, and the test asserts that refusal (OPERATIONS.md, Drill evidence, 2026-10-03).

Open, per OPERATIONS.md: the trust set in the pin, the re-signing decision, the rotation entry record, revocation, and a nomo command. A retired key stays answerable while its .spki exists, so a retired key is retired, not revoked.

Until these exist, OPERATIONS.md's guidance is to pin out of band with nomo init --from-spki, keep the old public key, and treat rotation as a deliberate re-anchoring that accepts the pre-rotation entries will not verify against the new key.

7. Policy

7.1 Grammar

Source: OPERATIONS.md, Policy grammar quick table.

  • Format: YAML. Version 1 uses ordered rules, first match wins. Unknown versions fail closed.
  • match.class: r0, r1, r2, r3 or a list. Reversibility class after registry evaluation.
  • match.tool: tool id or list, for example postgres.row.delete.
  • match.connector: connector id or list, for example postgres or s3.
  • match.workspace: workspace name or list.
  • match.blast_radius: exactly one of lt, lte, gt, gte with an integer. An unmeasured blast radius never matches.
  • decision: allow, deny or hold. Required.
  • seconds: required for hold; whole number from 1 to 900.
  • notify: cli, slack or a list (approval channels).
  • rationale: recommended string shown in denials and holds.

Unknown keys and unknown values are load errors. A missing or invalid policy denies startup in fail-closed posture.

7.2 Starter policy

version: 1
rules:
  - match:
      class: r0
    decision: allow
    rationale: fully reversible calls can proceed after ledger append
  - match:
      class: r1
      blast_radius: { lt: 100 }
    decision: allow
    rationale: small reversible writes are below the hold line
  - match:
      class: [r2, r3]
    decision: hold
    seconds: 120
    notify: [cli]
    rationale: visible or permanent damage needs a human decision
  - match: {}
    decision: deny
    rationale: deny anything the policy did not name

Note the rule ordering: a narrow rule must come before a broad one, since first match wins.

7.3 Attribution in the ledger

Each decision record binds attribution.policyDigest (the digest of the canonical policy content in force) and attribution.rule (index and rationale of the rule that fired) into the signed body (THREAT-MODEL.md section 3.2, citing packages/policy/src/digest.ts, packages/proxy/src/forward/tools.ts:376, packages/ledger/src/canonical.ts:101). Records written before attribution existed still verify because the hash is over the body as written. There is no migration (THREAT-MODEL.md section 3.2).

Observe-only records allow with no rule. The record names the policy but not the rule it would have refused (THREAT-MODEL.md, citing packages/proxy/src/bin.ts:659-663).

7.4 Approvals

The proxy surfaces held calls through a per-run state directory with pending.json, proxy.lock and decisions/<nonce>.json. A single proxy owns a directory at a time; a second live proxy refuses with ApprovalStateInUseError. A stale lock may be removed by hand after a crash (OPERATIONS.md, Approvals).

Approve or deny with the CLI writes a decision file and reports it as queued. The running proxy polls and resolves the hold. The CLI does not claim the release, because it cannot know whether the proxy was still running when the decision landed (OPERATIONS.md).

The policy is reloaded per request. An agent may not supply its own workspace, adapter identity or approval grant to the managed MCP server (RECOVERY-CONTRACT.md, Trust boundary, as quoted in the earlier read).

8. Connectors and recovery contract

8.1 Classification axes

Source: packages/connectors/src/recovery.ts (read in full, SHA 85cebb837b357b59cbdd8e8bd79caa3fed821508).

Effect: read, write, external-disclosure, mixed or unknown.

Reversibility: r0, r1, r2, r3 or unknown.

Readiness: verified, conditional, expired, unsupported, unknown-outcome or conflict.

Reversibility belongs to a call under declared preconditions, not to a tool permanently (CONTEXT.md). R0 does not mean read-only: a read can disclose information irreversibly, which is why the effect axis is separate. R1 restores declared state but does not erase logs or transaction history (THREAT-MODEL and context pack, as quoted; the exact definitions are in RECOVERY-CONTRACT.md, which was read only in truncated form, so the R2 and R3 definitions below are from the context pack and the policy grammar, not from the full contract).

8.2 Observation shape

Each observation returns effect, reversibility, readiness, scope, resources, revision (a JSON value), an optional read set, and blast radius. The read set is optional, and its absence means the adapter reports no read set, not that it read nothing. A planner that cannot prove a dependency must not order around it (recovery.ts, Observation type).

Blast radius has a count (number or null) and a precision of exact, bounded or unknown. Unknown blast radius is not zero (CONTEXT.md).

8.3 Adapter interface

RecoveryAdapter (recovery.ts) has these members:

  • id and version.
  • preflight(args): returns an Observation.
  • prepare(args, observation, operationId): returns Prepared (before state and plan). It must revalidate the observation and own atomicity and compare-and-swap at the write boundary.
  • execute(args, prepared, operationId): returns Outcome (result and evidence).
  • release(operationId): releases preparation resources before dispatch or after an execution error. It never retries.
  • reconcile(operationId, prepared): returns unknown, failed or succeeded with an outcome.
  • recover(prepared, outcome, recoveryId): returns RecoveryOutcome, status restored, compensated or conflict, with evidence. It must guard against drift and verify the declared scope before reporting restored.
  • recoverWithContinuation (optional): narrowly scoped continuation for a verified recovery job.
  • reconcileRecovery (optional): reads durable recovery evidence only. An absent receipt never authorizes another inverse.
  • reconcileRecoveryWithContinuation (optional): lineage-bound counterpart.

A RecoveryContinuation is runtime-derived proof that the immediately newer operation in a job was restored. Callers cannot supply it to standalone recovery (recovery.ts).

Classification metadata alone is not an adapter (recovery.ts, file header).

8.4 Connectors in the repository

The repository names filesystem, postgres and s3 connectors, and a git connector that shells out to git (packages/connectors/src/git/managed.ts:22, managed-commit.ts:1020, per THREAT-MODEL.md section 1.1). Connectors are in-process modules, not child processes, except git. Their individual recovery coverage is in docs/RECOVERY-COVERAGE.md, which was not read in this revision. The paper makes no coverage claim for any connector.

8.5 Recovery jobs

A recovery plan for one run or an explicit operation list is signed and digest-bound. Recovery requires the exact plan digest and separate operator authorization. A changed plan is refused. Human drift is a conflict (RECOVERY-CONTRACT.md, as quoted in THREAT-MODEL.md section 8). Recovery writes a new signed event linked by reverses, and never deletes original evidence.

Job states: planned, approved, applying, checkpoint, restored, partial, conflict, unknown, paused. A restart after an inverse and before its checkpoint reads the receipt and does not repeat the inverse. Compensation makes a job partial, never restored.

Interrupted dispatch is unknown and is never retried automatically. An absent receipt is not proof that nothing happened.

Limits, from RECOVERY-CONTRACT.md as quoted: a blast radius of unknown cannot pass an exact count limit; filesystem undo is bound to the original path and inode revision, and a moved managed root returns conflict rather than rebinding; a point-in-time restore is not an inverse; recovery is not generalized to unsupported hosts or tools.

8.6 Idempotency and dispatch

Durable capture precedes dispatch. Workspace and operation id identify one immutable request. Reuse with another request or adapter version is refused (RECOVERY-CONTRACT.md, as quoted).

9. Harness

The Harness is the coding-agent host integration. Its requirements, in the MVP spec and context pack:

  • Its runs use the same identity, token, proxy, policy and ledger path as other managed agents.
  • The Sunday demo runs one constrained task through the Workbench path. Learning is disabled for the demo.
  • Learning proposals stay inert until the operator approves the exact proposal digest. Retrieval is later, bounded, same-workspace and limited to approved, verified records. Learning never changes policy, permissions or credentials.
  • Harness proposals cannot change policy, permissions, host commands or credentials (MVP spec, Security requirement 8).

The demo makes no claim that persistent learning or a product-v1 Harness is complete.

The Workbench owns the trusted local demo principal and obtains the run token outside the model prompt. It must not store the run token in a public config response or tool result (MVP spec, Architecture boundaries).

Harness source was not read in this revision. Claims about its internal behavior are limited to the requirements above.

10. Threat model

10.1 Assets and adversaries

Assets: the integrity of the ledger chain and its signatures; the run token and upstream credentials; the policy file; the target systems the proxy protects.

Adversaries from the threat model (THREAT-MODEL.md section 1 and 9 as read), in summary:

  • An agent that submits an unknown or unclassified tool.
  • An agent that submits a high-risk write without approval.
  • An agent that edits the ledger after the fact.
  • An agent that truncates the ledger.
  • A third party with read access to the signing key file.
  • An attacker who replaces the signing key file on the same host.
  • A malicious upstream with access to its own environment.
  • A database superuser.

10.3 Out of scope in the current repository

  • Shell, network, browser and third-party actions outside the managed executor. Local mode is cooperative (RECOVERY-CONTRACT.md, Trust boundary, as quoted).
  • A distinct operating-system principal for the recorder. None exists in the source tree (THREAT-MODEL.md section 4.2).
  • Non-repudiation, and a verified human identity behind approvals.
  • Multi-tenant isolation, SSO and hosted key management.

10.4 Limits of the signature

Against a third party who can edit the JSONL but cannot read the key file, the signature is real and does work. Against an agent with code execution as the same user, a plain local signature adds little on its own. The repository's own documents say so in several places (THREAT-MODEL.md section 3.3; OPERATIONS.md, The verification key is not the signing key).

What fail-closed does not guarantee (OPERATIONS.md, What fail-closed does not guarantee): that declared facts are true; that a human approval was authenticated; that a local JSONL store is safe for multiple writers; that R2 or R3 calls can be undone; that a replay is safe after target drift; that connector credentials exist; that production Postgres or S3 is wired by default.

10.5 Dispatch-time risks

  • Timeout after dispatch. Unknown outcome, reconciled against the target. Never reported as cancelled.
  • Stop after dispatch. The call is not cancelled and its effect is not reversed.
  • Grant expiry between approval and dispatch. Rechecked; reject or reissue.
  • Revocation with an unreachable node. Not reported as revoked (MVP spec, product v1).

11. Deployment modes

The repository documents:

  • Local CLI and workbench: dev JSONL ledger, local keys, STDIO proxy. Implemented.
  • Desktop: Tauri shell starts the Node runtime as a child; both run as the login user. Implemented.
  • Hosted control plane: Postgres ledger in a dedicated schema; cloud signing key from the environment. Partly implemented. Hosted features are a separate service and licence boundary (THREAT-MODEL.md section 2.1).
  • Sunday demo: loopback inbound HTTP MCP endpoint, local issuer, disposable target. Planned.

Air-gapped and sovereign deployments are not described in the reviewed source and are not claimed here. The local JSONL mode is the nearest existing shape because it requires no network service, but it is not an air-gapped deployment design and has its own limits (section 6.4).

Licensing. The public proxy spine is Apache-2.0 open core. Hosted control-plane features are a separate closed service boundary. The context pack requires a verified package and licence map before any claim about which features are open or hosted. That map was not read in this revision.

12. Verification and release gates

12.1 Sunday demo exit (planned)

Source: MVP spec, Sunday demo exit.

  • A single local Workbench run calls the proxy and the disposable target.
  • A read or low-risk call uses the fast path. Only the high-risk write uses the policy and approval path.
  • A valid 60-second run token is accepted. Wrong audience, wrong scope, expired and revoked tokens are refused before upstream dispatch.
  • Allow forwards only after a pre-dispatch append. Deny does not forward. Hold does not forward until exact-digest operator approval and a fresh grant check. Observe-only forwards only when explicitly selected.
  • Token and upstream secret redaction tests pass.
  • Local kill blocks the next call. An in-flight call is shown as unresolved if its completion is unknown.
  • The constrained Harness run reaches the proxy through the Workbench path.
  • pnpm run typecheck and pnpm test pass. No production account or non-disposable target is touched.

12.2 Product-v1 release gate (planned)

Source: MVP spec, Product-v1 release gate.

  • MCP HTTP authorization has positive and negative conformance tests: resource metadata, resource parameter, issuer, audience, scope, expiry, revocation, 401 challenge, and no upstream token passthrough.
  • Every active revocation target returns correct acknowledgement state. Offline nodes and dispatched work remain visible as unresolved.
  • The Harness uses the same identity, token, proxy, policy and ledger path.
  • Threat model, migration, backup, key rotation, incident response, event retention and tenant isolation have reviewed acceptance evidence.
  • Customer discovery establishes a specific pilot with a named owner, approver, incident owner, disposable environment and dated next step. This is separate from engineering completion.

12.3 Commands

From the MVP spec: pnpm run check (full check), pnpm test, pnpm run typecheck, pnpm run build. Node.js 24 or newer; pnpm workspace; React 19 and Vite 7 for the web UI. Tailwind CSS v4 is a requested target, not a current dependency. Focused proxy and Workbench tests use the Node test runner, with paths chosen in the implementation plan.

15. Glossary

  • Allow, Deny, Hold, observe-only: explicit policy outcomes. Observe-only is opt-in and visible.
  • Anchor: a signed head (headSeq, headHash, treeDigest) held outside the agent's writes, used to detect truncation or rewriting by a third party.
  • Attestation: a signed summary of a ledger slice.
  • Digest: a SHA-256 over canonical content. Payloads are not stored; digests are.
  • Fail closed: deny when identity, scope, policy, ledger or broker state cannot be confirmed.
  • Hold: a pending decision awaiting an exact-digest operator approval.
  • Observation: an adapter's report of effect, reversibility, readiness, scope, resources, revision, read set and blast radius.
  • Readiness: whether recovery is currently verified, conditional, expired, unsupported, unknown-outcome or in conflict.
  • Unknown outcome: a dispatch whose result cannot be confirmed. Never reported as cancelled or reverted.
