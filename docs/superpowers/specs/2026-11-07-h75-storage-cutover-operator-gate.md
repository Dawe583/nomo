## Deployment-owner handoff: exact evidence and decisions required

Open one protected change record for the proposed maintenance window. Before any cutover, the deployment owner must provide all of the following; the blank template is only a collection format, not evidence:

1. **Complete inventory:** independently accepted list of every supported executable, direct and managed launch path, exact release/commit and runtime, legacy/new lock protocol, effective configuration, and every resolved canonical workspace/account root with named owner. Include all install locations, `NOMO_HOME`/`VOID_HOME` overrides, global links, wrappers, services, aliases, and symlink/volume canonicalization. State the discovery method and coverage; a process sample or default-path list is insufficient.
2. **Enforceable fence:** control-plane or launcher evidence that denies all new old/new writers and stale reapers at every inventoried entrypoint and root. Include activation time and independent timestamped negative checks for managed and direct invocation. A notice, PATH edit, advisory lock, or stopping one UI is insufficient.
3. **Drain and stale-reaper barrier:** per-root process/admitted-operation census before and after the required grace interval; executable identities; proof all admitted work completed; proof every old reaper exited or crossed the stale-check/unlink/reacquire section; barrier time after second observation and before root drain acceptance. Keep fence active throughout.
4. **Preservation and integrity:** operator-approved restorable backup of each canonical root, including encrypted snapshots, key files, locks, SQLite databases, journals, and unknown files. Record source/destination identity, metadata, permissions, sizes, per-file hashes, and source-unchanged confirmation. Supply protected offline read-only integrity results using matching keys without exposing keys or plaintext.
5. **Controlled restart:** exact candidate release hash/runtime and conversion procedure; under the accepted fence/drain/preservation gates, one candidate writer per root must open the expected sentinel/database, read prior state, perform an approved reversible synthetic operation, then be reread by an independent fresh process. Attach root-specific command/output references, timestamps, identities, and unchanged backup/source hashes.
6. **Rollback and approvals:** exact prior release/runtime; compatible lock representation; encrypted restore point per root; preserved failed-state copy; fence/drain/reaper barrier; disposable-copy rehearsal with the exact prior and candidate builds; per-root restore and integrity results. A rollback owner, verifier, release operator, and deployment approver must be distinct where the register requires; the local preflight requires the approver name to differ from the rollback owner, rollback independent verifier, and release operator after trimming and ignoring case (this compares name text only). Provide separate timestamped gate decisions and the deployment owner's final maintenance-window/final-GO approval after independent review.

Attach immutable, protected artifact references and exact command outputs to the change record. Redact secrets and never put keys, plaintext, or production payloads into the repository, graph, or shared logs. If any item is missing, stale, sampled-only, unauthenticated, or not independently verified, leave the decision **NO GO**. The agent must not inspect live systems, fill the register with inferred claims, or execute the cutover.

3. **Enforceable maintenance fence.** Before draining, prevent all new old and new writers and reapers from starting through every inventoried launcher and direct entrypoint. Fence must cover workspace and account roots and be observable and fail closed. A UI notice, stopping one TUI, PATH edit, version check, advisory lock, or assumption that no process is active is not a fence. The owner records the enforcement mechanism, scope, activation time, independent per-entrypoint denial check, and independent per-root denial check, including evidence that direct invocation cannot bypass the fence.
4. **Drain including stale reapers.** With the fence active, enumerate every process with access to each canonical root and wait for all admitted critical sections to finish. Also account for old stale-reaper code that already validated a dead PID and may be paused before unlink/reacquire; ordinary process sampling or no open file descriptor is insufficient because the legacy protocol can unlink by pathname after validation. Prove these reapers have exited or reached a barrier beyond the unlink/reacquire section. Record per-root process identities, executable versions, drain evidence, and a second observation after the required grace interval. Each root's stale-reaper barrier timestamp must follow that second observation and precede its drain check. No new sentinel-aware writer may start before this barrier.
5. **Preserve and validate state.** Before any conversion, create an operator-approved restorable backup/snapshot of each data root and record path, metadata, ownership, permissions, size and cryptographic hashes without exposing secret contents. Preserve encrypted snapshots, key files, lock artifacts, SQLite databases, journals and unknown files. Do not delete, truncate, rename, replace or reinterpret a legacy lock as stale based only on PID liveness. Validate copied encrypted state by an approved offline read-only integrity check using the matching key material in its protected environment; record pass/fail and confirm source bytes/hashes remain unchanged. Never put keys or plaintext in logs.
6. **Restart gate.** Only after inventory, fence, drain, backups, integrity checks, and an exact lock-format conversion plan are independently accepted may the owner allow the sentinel-aware release to start. Start one controlled writer per canonical root first. Verify it opens the expected sentinel and nested SQLite database, reads the prior state, performs an approved reversible synthetic/local operation, and that an independent fresh process reads the same preserved state. Then admit remaining approved sentinel-aware writers. Keep old versions fenced. For every controlled root, record release hash and runtime matching the gate-level candidate values, root, lock type, read/write/re-read evidence and operator/verifier identities.
7. **Separate rollback plan and proof.** Review rollback independently before cutover. Define the trigger, decision owner, fence retained during rollback, exact prior code and runtime (both recorded as separate required fields), explicit compatible lock representation, encrypted-state restore point, and per-root procedure. The register requires the proposed lock representation as text and a separate encrypted-state restore-point evidence URI; preflight does not establish compatibility, readability or restorability. Rollback rehearsal and execution must keep the maintenance fence active. The register records an explicit fence-retained assertion and a protected evidence reference; preflight checks only these submitted fields and does not verify the fence state. The rollback rehearsal must follow acceptance of the drain and controlled restart gates. Rollback must first fence new launches and drain every sentinel-aware writer, then preserve the failed state before rehearsal/restoration and restore/validate the approved backup or a proven compatible state. The register records rollback fence and drain timestamps followed by the failed-state preservation assertion, UTC time and protected evidence reference before the rollback rehearsal; preflight verifies only their submitted shape/order. Do not let old PID-lock code run against a directory sentinel and do not remove or convert a sentinel while any old/new process or prevalidated reaper can act. Each rollback root row records an explicit admitted-writers-drained assertion and timestamp after rollback drain, a legacy-writers-absent assertion, and a stale-reaper barrier timestamp after writer drain and before the restore check. It also records a per-root assertion, protected reference and check timestamp for lock compatibility with the prior runtime. The check timestamp must follow the reaper barrier and precede the restore check; preflight validates only submitted values and references. Test rollback on a disposable copy with the exact prior and candidate builds, including restart and state-integrity checks for every canonical root. Record both prior and candidate release hashes; the candidate hash must match the restart gate. This is a register consistency check, not proof those builds were used. Each rollback root row also records a separate encrypted-state restore-point evidence URI alongside the gate-level restore-point reference, restored prior release hash, runtime, integrity result reference, and check time after rehearsal and before rollback acceptance. This checks reference coverage only, not encrypted data readability or restoration. A code checkout or package downgrade alone is not a data/lock rollback. Do not reuse cutover approval as rollback approval. The preflight checks this submitted chronology only; it does not establish that either approval or cutover occurred.

## Local evidence-register preflight

Start from `scripts/src/h75-cutover-register.template.json`; it is intentionally incomplete and must fail closed until the deployment owner replaces every blank and supplies real evidence. Do not treat the example values in tests as operational records.

Run `node scripts/src/h75-cutover-preflight.mjs <evidence.json>` on the deployment owner's change-record export before independent review. The JSON register has `schemaVersion: 1` and one section per gate: `inventory`, `fence`, `drain`, `preservation`, `restart`, and `rollback`. Every section records named owner and independent verifier, `decision: "accepted"`, and the same non-file URI `recordRef` with a non-empty authority (for example, `change://...` or `artifact://...`). Inventory enumerates entrypoints and canonical roots; fence proves denial for every entrypoint and canonical data root; drain covers every canonical root, timestamps follow fence activation, each root check follows the second observation and precedes drain acceptance, and the second observation follows the first and the observations span the recorded positive grace interval. Preservation, restart and rollback fields follow the evidence table above. The fixture in `scripts/src/h75-cutover-preflight.test.mjs` is an example of the shape, not real evidence.

A companion shape reference is available at `scripts/src/h75-cutover-register.schema.json` (JSON Schema draft 2020-12). The source-level tests compare its gate and row property sets with the executable preflight and check that the blank template has the same keys and fails closed. Every gate requires a real UTC `decisionAt` timestamp; this checks only the submitted value's shape, not the truth or authority of the decision. These tests do not execute a JSON Schema validator: the schema is not wired into the CLI and cannot check cross-section coverage, canonical-root identity uniqueness, references, or timestamp ordering. The executable preflight remains the behavior source of truth. The restart gate decision timestamp must be at or after every per-root restart check timestamp. Its preservation check rejects a destination root ID that equals the source root ID. This is a register-level identity check only; it does not verify physical storage independence. Its inventory check rejects repeated paths after lexical normalization of absolute paths, including `.` and `..` segments. It does not resolve symlinks, case/volume aliases, or inspect local filesystems. No JSON Schema validator dependency is installed or required by this tool.

This command reads only the specified JSON file. It does not inspect processes, launchers, roots, backups, or referenced artifacts and cannot prove that their contents are true. A successful result means only that the submitted register is structurally complete for independent review. It is not a maintenance fence, cutover authorization, or GO decision; the decision section below remains authoritative.
