# H4 design proposal A: profile store joins the evidence chain

Lens: minimal blast radius, fail closed. Owner: controller session, 2026-10-29.
Decision under design: D4 (DECISIONS.md, 2026-10-21): skill and subagent promotion
stays proposal-only until a profile store joins the evidence chain. Until then the
agent tools for those kinds remain disabled.

## 1. Expected behavior

A promotion of a skill or subagent profile is a signed, digest-bound operation
that a third party can replay and verify from the chain alone, and that can be
rolled back to the exact prior profile with the same evidence quality as an entry
rollback. Promotion never widens authority silently: the parent scope checks that
already exist in `approveHarnessProposal` stay mandatory and become part of the
signed record.

## 2. Contract

The profile store already exists in derived form: `promotedAgentProfiles(workspace)`
replays `harnessRefinement.profiles` records from the signed chain, validating
digest binding and before/after consistency. H4 does not add a new store. It adds
a dedicated record shape and a dedicated rollback path so the profile lifecycle is
symmetric with the entry lifecycle instead of being a side effect of a proposal.

New record kind, written through `commitWorkspace` exactly as other records:

- `event`: `profile:promoted` for activation, `profile:rolled-back` for rollback.
- `harnessProfile` body field: `{ digest, atSeq, parentDigest?, changes: [{ id, before, after }] }`.
- `digest` is the proposal digest, already approved by the operator and present in
  `pendingForWorkspace` at `atSeq`. The record is refused unless the chain length
  still equals `atSeq` at write time, exactly as approval already requires.
- `changes` carries both snapshots. `before` is `null` for a create, `after` is
  `null` for a delete. This is the same shape `profiles` already uses, so
  `promotedAgentProfiles` replays it without change.

Placement: keep the profile validation and parent scope checks inside
`approveHarnessProposal`, where they already live. Move only the construction of
the `harnessProfile` record and its rollback inverse into a small helper,
`profilePromotion.ts`, beside `refine-pass.ts`, so the two paths cannot drift.
No new persistence, no new transport, no new dependency.

## 3. Additive migration

Records written before this change carry `harnessRefinement.profiles` and no
`harnessProfile` field. `promotedAgentProfiles` keeps reading the old field as a
fallback for any record that lacks `harnessProfile`, so old chains replay
unchanged. A record with neither field is simply skipped, as it is today. No
migration tool, no rewrite of history, no schema version bump.

## 4. Failure modes, all fail closed

- Unknown profile on rollback: refused with "no activated promotion matches that
  digest", same wording family as entry rollback.
- Digest mismatch between the profile record and its refinement: already thrown
  by `promotedAgentProfiles`; keep it.
- Before/after mismatch on replay: already thrown; keep it.
- Chain moved after review: approval already refuses; promotion inherits it.
- Profile exceeds parent scope: already checked; keep it.
- Collides with a built-in agent or preset: already checked; keep it.
- Already rolled back: refused by name, same as entries.
- A later promotion displaced it: refused by name, same as entries.
- Empty promotion (no profile edits): refused with "no supported edit to
  activate", already present.
- Secret-like content in any profile snapshot: re-scanned at write time, as
  rollback already does for entries.

## 5. Test plan (named, failing before implementation)

- `harness-profile-promotion.test.ts`: a promotion writes `harnessProfile` with
  `digest`, `atSeq`, and `changes` carrying before and after; a replay of the
  chain returns the promoted profile; a second promotion of the same id is
  refused.
- `harness-profile-rollback.test.ts`: rolling back by digest restores the prior
  profile and writes `profile:rolled-back`; rolling back again is refused by
  name; a later promotion blocks rollback of the earlier one until it is rolled
  back first.
- `harness-profile-migration.test.ts`: a chain containing only the legacy
  `harnessRefinement.profiles` field replays to the same store.
- `harness-profile-scope.test.ts`: a profile exceeding parent tools, policy,
  turns or context is refused and writes no record.

## 6. Security consequences

- Promotion is evidence, not authority. The promoted profile becomes available
  to spawn only after the operator approves the exact digest, and only within
  the parent's tool and bound limits, which are re-checked at activation and
  recorded in the signed body.
- A promotion cannot bypass the policy engine: `policyProfile` of the promoted
  profile is clamped to the parent's policy profile, as today.
- Rollback re-scans snapshots for secrets, as entry rollback does.
- No profile is ever written outside `commitWorkspace`, so it is signed by the
  same key as every other record.

## 7. Rejected alternatives

- A separate profile store table outside the ledger. Rejected: it would create a
  second source of truth for the same fact, and `promotedAgentProfiles` already
  proves the chain is sufficient. Two stores would fork under a crash.
- Promoting on proposal creation rather than approval. Rejected: a mined proposal
  is evidence, not authority, and a model must never gain a tool surface without
  an operator digest.
- Letting profile promotion skip the parent scope checks when the operator
  approves. Rejected: approval is not a grant of authority beyond the parent;
  the checks are the safety property, not a UX step.

## 8. Open questions for the owner

1. Should skill promotion (markdown skill, not subagent profile) share this
   record kind, or get its own `skill:promoted` event with skill content?
2. Should a profile promotion be a separate CLI and control plane command, or
   stay folded into `approveHarnessProposal` as it is today?
3. May a promoted profile outlive the session that created it, or only the
   workspace? The current replay is workspace scoped; cross-workspace promotion
   is out of scope for v1.
