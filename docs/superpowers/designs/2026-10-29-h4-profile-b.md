# H4 design proposal B: profile store joins the evidence chain

Lens: the operator value loop. Owner: controller session, 2026-10-29.
Decision under design: D4 (DECISIONS.md, 2026-10-21): skill and subagent promotion
stays proposal-only until a profile store joins the evidence chain. Until then the
agent tools for those kinds remain disabled.

## 1. Expected behavior

An operator promoting a skill or subagent profile sees exactly what will change,
approves one digest, and the change lands in the signed chain with both snapshots.
Later, the operator can roll it back by the same digest and see what was restored.
A third party with the chain and the verifier can reproduce both decisions without
trusting NOMO, the operator account, or the running process.

## 2. Operator surface

Before approval the operator sees, in the review surface already built for H3:

- the proposal summary, rationale and expected outcome;
- for each profile edit: the profile id, the current profile as it stands (or
  "new" for a create), and the proposed profile in full;
- the parent bound that limits it: parent tools, policy profile, max turns and
  max context tokens, so the operator can see why a tool is allowed or refused;
- the exact digest and the chain position at which approval is given.

After approval the activation record carries both snapshots, so the operator can
later inspect "what did this promotion actually change" without re-running it.
After rollback the rollback record names the restored profile ids and the
digest it undid, so the operator can tell which promotion was reversed.

## 3. Contract

Promotion reuses the existing approval path. No second approval system, no second
digest, no second record family. The change is that the profile section of the
activation record becomes a first-class, required-when-present store rather than
an optional side channel.

Record shape, written through `commitWorkspace`:

- `harnessProfile`: `{ digest, atSeq, changes: [{ id, before, after }] }`.
- `digest` equals the proposal digest and the `harnessRefinement.digest`. The
  mismatch check in `promotedAgentProfiles` already enforces this; H4 keeps it
  and makes it a documented contract rather than an implementation detail.
- `changes` replay in chain order. A create has `before: null`; a delete has
  `after: null`. An update carries both.
- `profile:promoted` is added to `harnessLifecycle.events` when changes exist,
  and `profile:rolled-back` on rollback. The ratchet and any future audit read
  these event names.

Rollback is symmetric to entry rollback and already mostly exists: it reconstructs
the inverse profile changes by swapping before and after, checks the active store
still matches the signed `after`, and writes `profiles: { digest, changes }` with
`approvedBy: "rollback"`. H4 documents and freezes this as the contract, and
requires that a rollback of a promotion with no entry edits still succeeds when
profile changes exist. That case is already handled by the `changed` check, which
includes `rollbackProfiles.length > 0`.

Placement: the profile validation and parent scope checks stay in
`approveHarnessProposal`. The construction of the `harnessProfile` record and its
rollback inverse move into a helper, `profilePromotion.ts`, beside
`refine-pass.ts`, so approval and rollback cannot drift apart on the shape.

## 4. Additive migration

Chains written before this change carry `harnessRefinement.profiles` and no
`harnessProfile` field. `promotedAgentProfiles` keeps reading the old field as a
fallback, so old chains replay to the same store. A record with neither field is
skipped. No migration tool, no rewrite, no schema version bump.

## 5. Failure modes, all fail closed

- No matching activation for the digest: refused with "no activated refinement
  matches that digest".
- Already rolled back: refused by name.
- Displaced by a later promotion: refused by name, with the instruction to roll
  the later one back first.
- Active profile no longer matches the signed `after`: refused, because a silent
  drift would make the rollback restore the wrong state.
- Empty promotion: refused with "no supported edit to activate".
- Profile exceeds parent scope: refused, and no record is written.
- Secret-like content in a snapshot: re-scanned at write time.
- Chain moved after review: refused, inherited from approval.

## 6. Test plan (named, failing before implementation)

- `harness-profile-promotion.test.ts`: promotion writes `harnessProfile` with
  digest, atSeq and both snapshots; replay returns the promoted profile; a second
  promotion of the same id is refused.
- `harness-profile-rollback.test.ts`: rollback by digest restores the prior
  profile and writes `profile:rolled-back`; a second rollback is refused by name;
  rollback of an earlier promotion is blocked until the later one is rolled back.
- `harness-profile-migration.test.ts`: a chain carrying only the legacy
  `harnessRefinement.profiles` field replays to the same store.
- `harness-profile-scope.test.ts`: a profile exceeding parent tools, policy,
  turns or context is refused and writes no record.
- `harness-profile-audit.test.ts`: the operator review surface receives the
  before and after snapshots and the parent bound for each profile edit.

## 7. Rejected alternatives

- A separate profile store outside the ledger. Rejected: two sources of truth
  for the same fact, and `promotedAgentProfiles` already proves the chain is
  sufficient. A crash would fork them.
- Promoting on proposal creation rather than approval. Rejected: a mined
  proposal is evidence, not authority. A model must never gain a tool surface
  without an operator digest.
- Letting the operator approve a promotion without seeing the before snapshot.
  Rejected: approval without the prior state is a blind grant, and the whole
  point of the signed chain is that the operator decides with evidence.

## 8. Open questions for the owner

1. Should skill promotion (markdown skill, not subagent profile) share this
   record kind, or get its own `skill:promoted` event carrying skill content?
2. Should promotion be a separate CLI and control plane command, or stay folded
   into `approveHarnessProposal` as it is today?
3. May a promoted profile outlive the session that created it, or only the
   workspace? Replay is workspace scoped; cross-workspace promotion is out of
   scope for v1.
