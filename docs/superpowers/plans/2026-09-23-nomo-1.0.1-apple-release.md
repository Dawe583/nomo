# NOMO 1.0.1 Apple Release Implementation Plan

> **For agentic workers:** Use superpowers:subagent-driven-development or superpowers:executing-plans after explicit approval of this plan. Execute one reviewed, testable slice at a time. This document authorizes no application-code change, credentials change, purchase, production mutation or store submission.

**Status:** planning only. User approved Mac, iPhone and iPad targets, with mobile as a client of an explicitly paired Mac or server. Detailed architecture below is a proposal for review, not an implemented capability.

**Goal:** deliver a trustworthy agentic recovery product for macOS, iPhone and iPad, suitable for external testing and subsequent submission as version 1.0.1, with claims limited to demonstrated capabilities.

**Architecture:** preserve the existing TypeScript recovery engine as the authority for policy, capture, durable outcome and Undo. Keep the existing Mac presentation/runtime where store feasibility permits. Build a native iOS/iPadOS companion that sends authenticated, narrowly scoped requests to an explicitly selected executor; it does not execute arbitrary local tools or recreate the recovery engine.

**Tech Stack:** existing pnpm/TypeScript/node:test, React and Tauri/Rust on Mac; proposed SwiftUI, URLSession, Security/Keychain and standard Apple frameworks on iOS. Prefer standard platform primitives and existing components. Do not introduce a second policy engine or custom cryptographic protocol.

**Spec:** product and acceptance contract in sections 1-5 of this document. Read alongside docs/CONTEXT.md, docs/DECISIONS.md, docs/STANDARDS.md, docs/RECOVERY-CONTRACT.md, docs/ADAPTER-CONFORMANCE.md, docs/RELEASE.md and docs/GUI-COMPACT-VERIFICATION.md. This proposal supersedes the iOS-local-executor and mandatory macOS SwiftUI rewrite direction in docs/APPLE-APPS-PLAN.md only after approval; do not silently treat both plans as simultaneously binding.

## 1. Confirmed decisions and explicit proposals

Confirmed:
- Target Mac App Store and iPhone/iPad App Store, not just a web Home Screen shortcut.
- Mobile is a companion to a paired Mac or server for the first release.
- A substantial full-GUI visual upgrade and richer reusable UI/UX components/icons are required, while preserving compactness.
- Keep the existing recovery safety invariants and use NOMO actively for bounded dogfooding.
- Plan before implementation. Version 1.0.1 is a release target, not today's proven readiness.

Recommended decisions for approval:
- Preserve Tauri on Mac unless a signed App Sandbox feasibility spike demonstrates an actual blocker. A SwiftUI Mac rewrite is not a prerequisite by preference alone.
- Use a native SwiftUI universal iPhone/iPad target; do not present a web wrapper as the finished native product.
- Initial executor support is one user-owned Mac; separately installed self-host/server mode is a later gated profile, not assumed ready.
- First end-to-end mobile slice uses an explicitly paired Mac over a trusted local network. This is not an internet-ready executor or public relay. The UI must explain network reachability.
- Define one executor protocol that can later support a separately verified server deployment. A user-controlled server profile may ship only after the same isolation/security tests pass. A managed public cloud executor, relay and billing are excluded from initial scope.
- Proposed iOS/iPadOS floor: 17.0. Mac floor remains the existing supported 13.5 unless the signed sandbox experiment proves another minimum is needed. Verify SDK/store submission requirements at execution time; deployment target and required build SDK are separate.
- Initial beta is free and invite-only. No in-app billing or promise of perpetual free inference. Provider charges are clearly disclosed. Pricing/IAP is a separate reviewed product decision before monetization.
- Use prerelease builds until gates pass. If 1.0.0 was never released, document why initial public marketing version is 1.0.1; do not imply a compatibility history that does not exist.

## 2. Product scope and non-goals

Mac essentials:
1. Select a workspace with explicit access consent; show executor, scope and supported operations.
2. Set up the intended provider without silent fallback; existing sessions retain provider snapshots.
3. Chat, approve a proposed action, capture before mutation, inspect outcome, preview Undo and confirm it.
4. Preserve human edits, handle unknown outcomes, survive restart and show retained history health.
5. Pair/revoke mobile devices; provide redacted support diagnostics and guided backup checks.

Mobile essentials:
1. Onboard and pair a trusted executor; visibly show identity, connectivity and permitted workspace.
2. Chat and view a durable activity timeline; display partial/unknown/conflict states truthfully.
3. Review exact changes, approve within granted authority and request Undo from an explicit preview.
4. Browse permitted documents/history; show unsupported/large previews without claiming completeness.
5. Resume after lock, suspension, network change or force-quit by fetching durable state, not replaying mutations.
6. iPad sidebar/detail layout, landscape, hardware keyboard and accessible large text.

Not in the first release:
- Universal Undo for arbitrary shell/editor activity or changes inside unrelated iOS applications.
- Local iOS shell/Node/MCP execution, a second Swift recovery core or autonomous offline writes.
- Cross-system atomic rollback, arbitrary rewind-by-time, distributed workers or leases without a separate design.
- S3/GitHub/Vercel write recovery advertised merely because an integration or registry entry exists.
- Automatic deletion of retained recovery evidence, automatic repair of corrupt state or key regeneration.
- A new plugin marketplace, hundreds of adapters, paid plans or a mandatory Mac rewrite.

## 3. Safety and protocol contract

These requirements apply to every task and transport:
- Capture and durable intent precede mutation. Unknown outcomes are reconciled; never automatically redispatched.
- Preview/digest is not authority. The executor separately verifies current authorization, scope and state.
- Recovery never overwrites a newer human edit. Conflict is a successful safety refusal, not a reason to force retry.
- An authenticated mobile device does not gain arbitrary filesystem or process access.
- Execute and Undo have independent permissions. Read-only pairing is a supported default.
- Host-scoped workspace identity comes from trusted configuration, not a user-controlled request field.
- Do not log keys, bearer credentials, pairing material, prompts or document bodies in diagnostic bundles.
- Read-only diagnosis does not secretly apply recovery, reconcile journals or mutate provider configuration.
- App Store and direct-distribution builds have explicit capabilities; direct-download features must not bypass store sandbox restrictions.

Proposed v1 protocol requirements, to freeze in a reviewed spec before implementation:
- Capability negotiation returns protocol version, executor identity, build, workspace identifier, supported operation/adapter versions and documented limitations. Unsupported versions fail closed.
- Server-side requests bind device identity, session, workspace, action and stable operation identifier. Recovery approval additionally binds exact digest, expiry and a single-use grant/nonce where applicable.
- Request identity preserves JSON-RPC string versus number exactly. Numeric-looking strings and large numeric strings are never coerced.
- Cancellation stops further forward work where possible; it is not evidence that an already dispatched side effect did not happen.
- Read event streams use bounded replay cursors. Cursor expiry triggers a snapshot reload. A disconnected client never forces an implicit mutation retry.
- Mutating actions carry stable idempotency identity, but idempotency must not be misrepresented as atomic distributed exactly-once execution.
- Device revocation is checked on active sessions and new requests, not just at pairing. Refresh/token replay and stale grants are rejected.
- Foreground-only reconnect is sufficient initially. No promise of continuous mobile background execution; push, if later added, carries an opaque hint and is never authority to execute.

Pairing proposal:
- User starts pairing on the executor, receives a short-lived, single-use invitation and explicitly confirms the mobile device and workspace scope.
- Use established authenticated transport and platform cryptography. A QR invitation must bind executor identity; do not trust an arbitrary certificate or disable TLS validation globally.
- Keep the existing loopback desktop API private. Add only a narrow authenticated companion endpoint; never expose the workspace operator token as a device credential.
- Use explicit QR/manual endpoint discovery first. If Bonjour is introduced, add correct usage/service declarations and test permission denial, IPv6, Wi-Fi isolation and IP changes. ATS/TLS behavior must be verified, not bypassed via blanket exceptions.
- Define secure local-network TLS/bootstrap in the protocol ADR, including certificate replacement behavior, expiry, rate limits, Keychain storage and re-pairing. No custom crypto implementation.
- Pairing QR/logs/screenshots must not retain reusable secrets. Revoke and re-pair after device loss.
- Initial pairing requires local unlocked-Mac confirmation. Recommended first-beta default: reject new remote mutations while the Mac is locked or its secure key is unavailable; do not queue them for automatic later execution. Already dispatched effects retain their actual durable outcome. Any unattended-execution option needs a separate explicit policy/review.
- One authorized device approval suffices initially. Concurrent duplicates bind to the same retained operation; this is not a two-person approval quorum.
- Repeated request ID with changed content refuses. Executor time governs expiry; mobile clocks are not trusted. Offline approvals remain visibly unsent drafts and require fresh review/confirmation after reconnect.
- Remote server mode requires equivalent authentication, TLS, workspace isolation and operational ownership. Do not expose the existing loopback server to 0.0.0.0 as a shortcut.

## 4. Definition of release-ready

No finite test suite proves 100% correctness. Use measurable release gates instead:
- Zero unresolved severity-1 data-loss/authentication defects or severity-2 blockers in the advertised scope.
- Zero unexplained test failures, no newly skipped tests to achieve green, no reduced assertions or weakened typechecking.
- Clean installation and exact-build tests on each advertised platform; actual iPhone and iPad evidence, not browser emulation or mobile-sized macOS WebView.
- Demonstrate write/preview/Undo, drift refusal, denied authorization, restart, lost response, duplicate request and revoked-device refusal end to end.
- Restore a complete retained-state backup in isolation and verify both history and recoverability; fail closed for missing/wrong key or incomplete artifacts.
- Initial performance budgets: cached local navigation p95 <=200ms; visible action acknowledgment <=300ms; local workspace ready <=5s on a recorded reference Mac; event presentation <=1s after executor acknowledgment on the test LAN. Provider generation time is measured separately, not included in these UI claims.
- 60-minute bounded transport load with no steadily growing pending maps/queues after load stops; reject excess work predictably rather than consume unbounded memory.
- VoiceOver, Dynamic Type, keyboard navigation, contrast, focus, reduced motion, 44pt mobile targets and no clipped primary action.
- All signing, provisioning, privacy, reviewer-access and platform metadata gates pass for the exact submitted binary.
- App Store acceptance remains Apple's decision. Submission readiness and approval are separate states.

Proposed beta exit evidence: at least 10 external testers across the supported device matrix, seven days without a known uncontained critical defect, at least 100 recorded successful scoped recovery journeys plus explicit conflict/unknown negative cases. This is an acceptance sample, not a statistical claim of perfect reliability. Increase the sample if failures expose new risk.

## 5. Execution workflow and evidence

For every implementation task:
1. Read the current source and relevant official documentation.
2. Add a minimal failing regression or an explicit failing feasibility check.
3. Record the red result for the intended failure, not missing tools or unrelated setup errors.
4. Implement only the task slice; preserve unrelated changes.
5. Run focused tests, typecheck, applicable integration/device tests and source review.
6. Attach exact commit, binary checksum, environment and sanitized evidence to the task.
7. Commit verified work to main under the user's standing authorization. Store upload/production changes require separate explicit approval.

TypeScript uses node:test and TAP. New Swift tests use the native XCTest/Swift Testing tooling, not JavaScript test emulation. New dependencies require a specific justification.

NOMO dogfooding:
- Current recovery MCP authority is only ~/.local/share/void-prime-dogfood/project with the existing five tools. Do not expand it, regenerate keys or claim shell/editor writes are intercepted.
- Use NOMO for actual supported writes/deletes/renames of test fixtures and staged planning artifacts; verify exact bytes/mode and recovery outcomes independently.
- Every experiment uses unique IDs, isolated nonsecret data and an evidence record. Preview before applying Undo. Reconcile unknown results; never blindly repeat.
- Cover normal write, delete, rename, repeated apply, restart, missing artifact, denied operation and deliberate external drift in disposable fixtures. Only intentional drift fixtures may use a clearly recorded external write.
- Repository edits, native builds, signing and store submissions remain outside this managed scope unless a separately approved integration is added. Label the boundary instead of inventing protection.
- Initial live probe already demonstrated relative-path write, exact bytes, preview and restored original absence. Absolute paths were safely refused with generic failed diagnostics; improve the tool contract without leaking filesystem secrets.
